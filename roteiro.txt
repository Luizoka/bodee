# Projeto: FaturaSync

Quero iniciar um novo projeto chamado **FaturaSync**.

A ideia é criar uma **API independente para automação de coleta de faturas**, inicialmente da Equatorial Energia, que possa ser consumida por diferentes sistemas meus.

Hoje tenho pelo menos dois consumidores potenciais:

* um projeto de visualização de faturas, o **Mapa GD**;
* outro sistema de um cliente que precisa obter determinadas faturas mensalmente.

O FaturaSync deve esconder toda a complexidade da Equatorial. Os sistemas consumidores não devem precisar saber sobre Playwright, CAPTCHA, JWT da Equatorial, endpoints internos, Base64 etc.

A ideia conceitual é:

```text
Mapa GD ───────────────┐
                       │
Sistema Cliente ───────┼──> FaturaSync API
                       │
Outros sistemas ───────┘
                              ↓
                         Equatorial
```

---

# 1. Objetivo principal

A API precisa suportar dois modos de operação.

### Consulta sob demanda

Um sistema poderá solicitar:

```text
"Puxe agora as faturas deste cliente para esta competência."
```

Exemplo conceitual:

```http
POST /v1/sync
```

```json
{
  "clientId": "client_123",
  "competencia": "2026/08"
}
```

A operação deve ser assíncrona.

A API responde inicialmente:

```json
{
  "jobId": "job_xyz",
  "status": "queued"
}
```

E posteriormente:

```http
GET /v1/jobs/job_xyz
```

---

### Consulta mensal automática

Também deve ser possível cadastrar uma automação como:

```text
Cliente X
executar a partir do dia 09 de cada mês

Contas:
X
Y
Z
```

No dia 09, o sistema verifica a competência do mês atual.

Exemplo:

```text
09/08/2026
→ procurar competência 2026/08
```

Se encontrar:

```text
X ✅
Y ✅
Z ✅
```

a execução mensal é concluída.

Se acontecer:

```text
X ✅
Y ✅
Z ❌
```

o sistema deve:

* salvar X e Y;
* não baixá-las novamente;
* manter somente Z pendente;
* tentar Z novamente no próximo dia.

Isso continua até todas serem obtidas ou até atingir um limite configurável de tentativas/dias.

# 2. Arquitetura desejada

Não quero colocar tudo dentro de um controller ou serviço monolítico.

Separar pelo menos:

```text
FaturaSync

API
│
├── Clientes
├── Contas
├── Faturas
├── Automações
└── Jobs

Worker
│
├── autenticação Equatorial
├── consulta de faturas
├── download
└── processamento de PDF

Scheduler
│
└── cria os jobs mensais

Queue
│
└── controla execução, retries e concorrência

Banco
│
└── metadados

Object Storage
   └── PDFs
```

Tecnologias sugeridas:

```text
Node.js
TypeScript
NestJS
PostgreSQL
Prisma
Playwright
BullMQ
Redis
Object Storage compatível com S3
```

Podemos alterar alguma tecnologia caso exista justificativa, mas quero manter a arquitetura modular.

# 4. Fluxo confirmado da Equatorial

Já fizemos engenharia reversa usando uma sessão legítima no portal.

O frontend utiliza a API:

```text
https://api-pa-cliente.equatorialenergia.com.br
```

O JavaScript do próprio portal faz a consulta de débitos usando Bearer JWT:

```http
GET /api/v1/debitos/{contaContrato}?listarEmAberto=false
Authorization: Bearer {JWT}
```

e processa:

```js
response.data.faturas
```

Isso foi identificado diretamente no código carregado pelo portal. 

A resposta real que já testamos contém, entre outros:

```json
{
  "data": {
    "contaContrato": "...",
    "totalDebitos": "...",
    "faturas": [
      {
        "numeroFatura": "...",
        "valor": "...",
        "dataVencimento": "2026-07-24",
        "dataPagamento": "0000-00-00",
        "competencia": "2026/07",
        "codigoBarras": "...",
        "notaFiscal": "...",
        "obs": null
      }
    ]
  }
}
```

Também confirmamos o endpoint da segunda via:

```http
GET /api/v1/faturas/segunda-via/{numeroFatura}?contaContrato={contaContrato}
Authorization: Bearer {JWT}
```

A resposta tem formato:

```json
{
  "codigoTransacao": "...",
  "data": {
    "url": null,
    "base64": "JVBERi0..."
  }
}
```

`data.base64` é o PDF da fatura codificado em Base64.

# 5. Login da Equatorial

O login não deverá inicialmente ser reproduzido via HTTP puro.

O portal utiliza CAPTCHA invisível e mecanismos de segurança carregados pelo próprio frontend. O HAR mostrou uso de reCAPTCHA Enterprise e SDK da Transmit Security. 

Fluxo esperado:

```text
Playwright
↓
abre portal oficial
↓
preenche login
↓
preenche senha/data
↓
clica em entrar
↓
o próprio frontend executa:
  CAPTCHA
  antifraude
  cookies
  demais tokens
↓
login concluído
↓
capturar access_token
```

Depois disso, não continuar navegando pelo portal.

Usar:

```text
Playwright → somente autenticação
HTTP → todo o restante
```

O JWT retornado pelo login será utilizado como:

```http
Authorization: Bearer ACCESS_TOKEN
```

# 6. Cache da autenticação

Não fazer novo login via Playwright desnecessariamente.

Guardar a sessão/token de maneira segura.

Fluxo:

```text
job precisa consultar cliente
↓
existe token armazenado?
↓
sim
↓
tenta API Equatorial
↓
200 → continua
401 → autentica novamente
```

Não confiar somente no `expires_in`.

A validação prática deve ser a resposta da API.

---

# 7. Credenciais

As credenciais da Equatorial são sensíveis.

Nunca armazenar senha/data utilizada na autenticação em texto puro.

Implementar:

```text
criptografia em repouso
```

A aplicação deve descriptografar somente quando for iniciar o Playwright.

Nunca:

```text
console.log(password)
console.log(jwt)
console.log(cpf completo)
```

em produção.

Também sanitizar logs de erro.

# 10. Competência

Nunca selecionar simplesmente:

```text
faturas[0]
```

A fatura precisa ser encontrada pela competência desejada.

A API da Equatorial retorna:

```text
2026/07
```

Então para agosto de 2026:

```ts
const target = "2026/08";

const invoice = invoices.find(
  invoice => invoice.competencia === target
);
```

Se não existir:

```text
WAITING_INVOICE
```

e não:

```text
FAILED
```

Isso é uma situação normal.

# 13. Retries

O portal da Equatorial frequentemente fica indisponível.

O sistema precisa diferenciar:

```text
PORTAL_UNAVAILABLE
AUTH_FAILED
AUTH_TIMEOUT
CAPTCHA_REJECTED
TOKEN_EXPIRED
API_TIMEOUT
API_500
INVOICE_NOT_AVAILABLE
DOWNLOAD_FAILED
INVALID_PDF
UNKNOWN_ERROR
```

Não tratar tudo como:

```text
"Erro ao baixar fatura"
```

Alguns erros merecem retry automático.

Exemplo:

```text
PORTAL_UNAVAILABLE → retry
API_TIMEOUT → retry
API_500 → retry
INVOICE_NOT_AVAILABLE → próximo dia
TOKEN_EXPIRED → renovar login imediatamente
AUTH_INVALID_CREDENTIALS → não ficar tentando
```

Usar backoff.

Evitar várias tentativas seguidas contra um portal que está fora do ar.

---

# 14. Critério de sucesso

Uma conta só deve ser marcada como concluída quando:

```text
fatura encontrada
↓
segunda via obtida
↓
Base64 válido
↓
PDF decodificado
↓
PDF validado
↓
PDF processado
↓
arquivo salvo no storage
↓
registro salvo no banco
↓
COMPLETED
```

Receber `HTTP 200` sozinho não é suficiente.

---

# 15. Validação do PDF

Ao receber:

```json
{
  "data": {
    "base64": "..."
  }
}
```

converter:

```ts
Buffer.from(base64, "base64")
```

Validar pelo menos:

* buffer não vazio;
* assinatura `%PDF`;
* PDF consegue ser aberto por biblioteca;
* contém pelo menos uma página.

Somente então continuar.

---

# 16. Remover segunda página

As faturas novas da Equatorial ficaram muito maiores.

Anteriormente eram aproximadamente 50 KB e atualmente podem chegar a cerca de 500 KB, além de terem duas páginas.

Para o nosso uso, a segunda página é desnecessária.

Depois de obter o PDF:

```text
Base64
↓
Buffer
↓
PDF
↓
manter somente página 1
↓
gerar novo PDF
```

Pode usar `pdf-lib` inicialmente.

Algo conceitual:

```ts
const source = await PDFDocument.load(buffer);
const output = await PDFDocument.create();

const [firstPage] = await output.copyPages(source, [0]);

output.addPage(firstPage);

const bytes = await output.save();
```

Guardar:

```text
originalFileSize
processedFileSize
```

para medir o ganho real.

Não fazer otimizações destrutivas inicialmente.

Primeiro somente remover página 2.

Depois podemos estudar compressão adicional.

---

# 17. Storage

Não guardar Base64 no PostgreSQL.

Fluxo:

```text
Base64
↓
Buffer
↓
processamento
↓
Object Storage
```

No banco salvar somente:

```text
fileKey
hash
size
metadata
```

Podemos inicialmente usar armazenamento local em desenvolvimento e depois S3/R2/Supabase Storage/etc.

Não acoplar o domínio a um provider específico de storage.

---

# 18. Não baixar repetidamente

Uma vez obtida a fatura da competência:

```text
2026/08
```

não baixá-la novamente todos os dias.

No retry mensal:

```text
X COMPLETED → ignorar
Y COMPLETED → ignorar
Z WAITING → consultar novamente
```

Isso é essencial.

---

# 19. Hash

Após processar o arquivo, calcular SHA-256.

Guardar:

```text
fileHash
```

Isso permitirá no futuro identificar:

* arquivos duplicados;
* eventual alteração de PDF;
* integridade.

O FaturaSync também precisa proteger a própria API.



# 23. Concorrência

Não abrir dezenas de Chromiums simultaneamente.

A fila deve controlar concorrência.

Começar conservadoramente:

```text
Playwright auth concurrency: 2 ou 3
```

Depois medir.

Chamadas HTTP podem ter concorrência maior.

Separar filas, se necessário:

```text

invoice-sync
pdf-processing
```

# 24. Reutilização de autenticação por cliente

Um cliente pode possuir 3 contas.

Não fazer:

```text

```

```text

↓

↓
```

Isso reduz drasticamente custo e risco.

---

Essa última parte eu manteria exatamente assim para o agente: **não deixe ele construir banco, filas, CRUD e metade do SaaS antes de provar que o login automatizado é confiável**. Depois que isso estiver sólido, o restante é engenharia bem convencional.
